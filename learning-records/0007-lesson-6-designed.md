# 第 6 课交付：越聊越贵——把每次调用算成账（成本与 token）+ 教师预跑实证

2026-09-06。用户上完第 5 课后报到，按 lessons/0005 页脚预告（"下一课：M2 收官 · 成本与 token：定价、token 计数、max_tokens 预算、prompt caching"）交付 **M2 收官第 6 课** `lessons/0006-cost-tokens.html` 与实验脚本 `code/0006-cost-lab.py`。主题与两项取舍已与用户确认（AskUserQuestion）：① **caching = 概念 + 厂商对照**（不硬测/不展开显式 cache_control）；② **价格基准 = DeepSeek 当日价练手**（用户真实付费方）。设计记录见 KNOWLEDGE 回填前的本文件。

**本课核心心智（教学定调）**：把"agent 每轮读 usage 记账"讲成 Agent 独有的成本真相。一句话核心：**Agent 烧钱 = 输出单价高 + 每一轮重读全部历史**。模型是无状态函数、每轮都要把【全部历史 + system + 工具说明书】重新发一遍 → 对话越长，每轮 input 越大（越聊越贵，且贵得越来越快）。读得懂 usage（input / output / cache_read）、input/output 分开计价、max_tokens 封顶最坏输出账单、把每轮不变前缀交给缓存降重复读单价，才算把 Agent 算成账。

**教师预跑发现的"计划外但更值"的事实（2026-09-06，DeepSeek v4-flash / Anthropic 兼容端点）**：
1. **`usage.input_tokens` 在该端点是"缓存未命中"部分，不是完整 prompt**：原计划镜 2 想演示"input 随轮次线性涨"，首跑却发现 input 乱跳（495→63→66→17），几乎不涨——差点做出一个与预期相反的 decisive 实验。诊断（相同请求发两次）：第二次 `input_tokens=18 + cache_read_input_tokens=384 = 402`，与首跑 402 吻合 → **端点在自动前缀缓存，input_tokens 只报未命中新增、重复前缀进 cache_read（DeepSeek 原生"自动上下文缓存"透传到兼容端点的 usage）**。命中是"尽力而为"（同前缀跑热才亮，冷启动/前缀不同时 cache_read=0），且跨脚本运行也命中（TTL 足够长，同一 system+tools 前缀二次运行即读 cache）。
2. **`count_tokens(messages)` 在该端点可用且返回全量**：count 与 input+cache_read 完全相等（404=404），是"不受缓存干扰、完整 prompt 到底多大"的官方真值。
3. **因此 decisive 实验从"看 input_tokens 涨"改成"看完整 prompt 涨"**：完整历史（count_tokens / in+cache_read）**445 → 553 → 667**（每问 +100 左右，只涨不跌）；每轮模型调用都 ≈ 此刻完整历史（同问内第 2 次调用更大，因为工具往返被重读）；cache_read 384 → 512 → 640 越滚越大（自动缓存吃掉重复前缀）、新增 in 一直很小。这个设计反而**把 caching 从纯概念变成可实测**（cache_read 自己亮起来），且避免了"端点缓存时灵时不灵导致 input 单独看不可复现"的坑。
4. **max_tokens 截断 + thinking 共享预算实锤**：同句写 300 字散文，max_tokens=32 → `usage.out=32`、`stop=max_tokens`、**可见正文 0 个字**（thinking 吃光预算，你为 32 个输出 token 付了钱却一个字没见到）；max_tokens=2048 → end_turn、357 字。把第 3/5 课"thinking 与正文共享 max_tokens 预算"接到"钱"上。
5. **成本换算（flash 低谷价，今天周日全天空闲价：in ¥1.5/M、out ¥4.5/M、缓存命中 ¥0.05/M）**：镜 2 那场 3 问对话（新增 in 503、命中 3072、out 286，完整等效 3575）——完全不缓存 ≈0.66 分 vs 自动缓存 ≈0.22 分（省约 2/3）。放大 100 用户×30 问/天×30 天 → 不缓存 ≈199 元/月、自动缓存 ≈66 元/月（量级感）。缓存省的是"重复读的单价"，full 曲线照涨——教学上正好点破"缓存 ≠ 停止增长"。
6. **显式 cache_control 探针**：给 system 块发 `cache_control={"type":"ephemeral"}` **不报 400**，但 cache_creation/cache_read 不因其点亮 → 该端点缓存是自动的、cache_control 不"手动控制"。诚实口径写进课件：别假设 cache_control 一定生效，靠读 usage 确认（厂商对照：Claude 显式 cache_control vs DeepSeek 自动）。

**价格查证（2026-09-06）**：DeepSeek 自 2026-08-17 起峰谷分时计价，2026-08-23 起周末全天低谷价（今天周日按低谷）。v4-flash 低谷：未命中 in ¥1.5/M、命中 ¥0.05/M、out ¥4.5/M；高峰翻倍（3.0/0.10/9.0）。v4-pro 低谷 4.5/0.15/13.5。课件与脚本均标"以官方为准、价格会变"。

**ZPD 判断 / 对动手层的预测**：
- 挑战 A（给 0001 装账单仪表盘）的 decisive 自检是观察③："0001 只答一个'问题'就有两笔 input 在变大，为什么和镜 2 的'越聊越贵'是同一笔钱？" 正解：一次"上海天气"内部就有 ≥2 次模型调用（get_weather → report_weather 收尾），第 2 次调用重读了第 1 次往返（tool_use 记录 + tool_result）→ 历史内部就在涨；Agent 的成本 = 循环内每次调用的 input 加总，调用越多、历史越长，单位成本越高。"一个问题内部往返"与"对话被拉长"烧的是同一机制：**每一轮重读至今全部历史**。若用户答"因为工具调用也算钱/模型每次都想一遍"，要点破"是历史重读让 input 变大，不是调用次数本身"。
- 挑战 B（换高峰价重算）检验"成本公式与杠杆跟价格无关"：换价格后镜 2 曲线不变、只有账单金额翻倍；且能说出"砍对话变长的是①长对话截断/摘要，不是②缓存"。若用户以为"缓存能压对话变长"，要点破缓存只砍重复读单价。
- 潜在误区要盯：把 input_tokens 单独当"完整 prompt"（漏 cache_read）→ 得出"越聊不越贵"；把 max_tokens 当省钱旋钮；以为自动缓存 = 成本不再涨。
- 埋的后续钩子：对话多长该"截断/摘要/归档"（M3 记忆与上下文入口）；缓存命中率怎么在生产里监控（M6 可观测性）。M3 预告已写进 0006 页脚。
