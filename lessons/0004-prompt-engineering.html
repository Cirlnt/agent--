第 4 课 · 模块 M2 · 工程地基

话要放对抽屉：
system prompt 与工具说明书的分工

前三课你都在给"单个工具"写说明书（TOOLS 里的三行字）。今天往后退一步看全局：模型每轮还会读一份叫 system 的"全局章程"。同一条规矩，写进 system 还是写进某个工具的 description，常常是"整台 Agent 要不要越界"的分水岭。

使命：3 个月转 AI 应用工程师 约 60–80 分钟 需要：第 3 课跑通的环境（venv + 环境变量） 花费：几毛钱 token

面试官考 prompt 工程，最常问的一句是："一条行为规则，你是写进 system prompt，还是写进工具的 description？" 新手把能想到的话全堆进 system；老手心里有一张表：管"一个工具"的，去那个工具的 description / schema；管"整台 Agent、管工具之间取舍"的，才进 system。 但"管整台 Agent"听起来很抽象——本课的实验就让"分工错位"这件事看得见。

1 · 心智模型：模型每轮读四样东西，system 是唯一"整台 Agent"的抽屉

先升级第 2 课的一句话

第 2 课说"模型对一个工具的全部了解，只在 TOOLS 里那一个字典"。这句话要补上半句： 模型每轮真正"读"到的说明，其实有四样—— 

① system prompt    ← 整台 Agent 的全局章程（你是谁 / 只做什么 / 总流程 / 红线）
② 对话历史         ← 到目前为止 user / assistant / tool_result 在聊什么
③ tools            ← 每个工具各自的 name + description + input_schema
④ 你喂回的 tool_result ← 工具执行后的真实结果（第 1 课闭环的那一环）

system 和 tools 都是"说明"，差别在作用域：tools 里每一份说明书只属于它那一个工具； system 属于整台 Agent，每轮、每个工具都处于它之下。

三个抽屉，各装什么

  1. system —— 整台 Agent 的抽屉：身份、职责范围、整体边界、跨工具流程纪律。 例句："你是天气与时间专用助手；只做两类请求；无关请求直接拒绝，不要调任何工具。"
  2. 工具 description —— 单工具的抽屉：这一个工具何时该用 / 何时不该用（负例）/ 返回长什么样。 例句："仅支持北京、上海、巴黎、纽约；用户问其它城市不要调用本工具。"
  3. input_schema —— 参数合同：这一个工具的参数类型 / required / enum。 例句："city 必填 string，取值限于四个城市。"

分工判据（本课一句话核心，请记到能默写）

一句话记忆

这条规则只管"一个工具"→ 写进那个工具的 description / schema； 这条规则管"整台 Agent / 工具之间的取舍"→ 写进 system。 分不清时先问自己：删掉 system，这条规矩还在吗？如果"没地方可放"——那它本来就是 system 的活。

一个反直觉的实锤（为什么 description 守不住"整台 Agent 的边界"）

description 只对"这个工具该不该被调"负责。于是它天然有一个盲区： 如果用户问的事根本不需要任何工具（比如一句纯知识问答"珠峰多高"，模型自己就知道答案）， 那 description 层"别乱调我"的告诫根本不会触发——没有工具要被调，也就没有哪份 description 出来拦。 这种"零工具也能答的域外请求"，只有 system 里那句"这台 Agent 只做什么、其余不做"能拦下来。 这就是为什么本课要给你看三镜对比：同一组工具，规矩放 system 与摊进 description，行为差在哪。

先别往下翻。用记忆回答，答错没关系，"想不起来"本身在帮你记住。

「你是一台只查天气和时间的专用助手，除此之外的事都直接拒绝」——这句应该写进哪里？

实验里，镜 2（把"只做天气/时间"写进 system）和镜 3（不写 system、只把边界摊进每个工具 description），都面对"珠穆朗玛峰有多高"——一个不需要任何工具、模型凭知识就能答的问题。谁会拒绝？

工具菜单里挂着一个"联网搜索"万能工具，却不给这台 Agent 写任何 system。你问它"今天比特币价格是多少"，它最可能怎么做？

"先 get_weather 取回真实数据，最后才 report_weather 收尾；查时间就别套 report"——这条跨工具流程纪律，为什么放在 system 是结构上更正确的位置？

第 1 步 · 跑三镜实验

文件已写好：D:\agent学习\code\0004-prompt-engineering-lab.py。跑它：

python code/0004-prompt-engineering-lab.py

工具集是第 3 课的三件套（get_weather / get_current_time / report_weather）再加一颗雷：一个"联网搜索"通用工具。三镜唯一差别是规矩放哪：

# 镜 1 · 裸奔：没有 system，search_web 是万能版
q_weather 上海天气   → get_weather 正常点单                     （对照组：域内谁都对）
q_btc     比特币价   → ✳ search_web({query: 比特币价格 今日})     ← 它去联网搜了！
q_everest 珠峰多高   → 直接开口答 8848.86                        （通用助手，知识照答）

# 镜 2 · 同一工具集 + system 顶层定位"只做天气/时间"
q_weather 上海天气   → get_weather 正常点单
q_btc     比特币价   → 拒绝："我只负责天气和时间"                  ← system 边界生效
q_everest 珠峰多高   → 拒绝："知识问答超出职责范围"                ← 零工具域外也拦住了

# 镜 3 · 不写 system，只把边界摊进各工具 description（search_web 收窄成企业内网）
q_weather 上海天气   → get_weather 正常点单
q_btc     比特币价   → 拒绝："我没有查询比特币价格的功能"          （desc 自守起了作用：没工具适配）
q_everest 珠峰多高   → 直接开口答 8848.86                        ← 漏了！desc 层看不见零工具请求

盯住 q_everest 那一列：镜 2 拒了、镜 3 答了——工具一模一样，只差"这台 Agent 的边界写没写进 system"。 镜 3 为什么守住了币价却漏了珠峰？因为币价"要调工具去查"，description 层能拦；珠峰"不需要任何工具"，没有哪个 description 会被触发去拦它。

诚实提醒（教师实测，必读）：分工的价值不在"今天这模型放错会崩"，而在作用域

备课我先跑过另一组小实验：只有天气 + 时间 + 出口工具、问句又都在域内时，deepseek-v4-flash 连 system 都不写也守得住顺序——先查后报、查时间不乱套 report。 为什么？因为出口工具 report_weather 的 schema 强制要一个 condition（形如天气串），而真正能给它的只有 get_weather——数据结构已经把顺序物理锁了大半。 所以本课不吓唬你"不放 system 就崩"；分工真正的收益在于：① 菜单变杂（有万能工具）或用户问域外时，没有顶层定位的 Agent 会自己扩张成"通用助手"（镜 1）；② 边界放对抽屉，是作用域正确，换更复杂的 Agent、换别的模型时它才站得住。看问题要看到这一层，别停在"我这模型乖，所以无所谓"。

陷阱①：description 的"自守"各自为政，合起来不等于整体边界

镜 3 里每份 description 都很守规矩（连 search_web 都收窄成"只搜企业内网"）——币价因此被拦下。 但整台 Agent 的边界，从来不是"所有工具自守的加总"：只要有一类请求不需要任何工具，加总里就永远缺它那一格。 面试时把这一点讲出来（"description 管工具用不用，system 管 Agent 该不该接这个活"），是比背定义高一大截的回答。

陷阱②：只给工具不给定位 = 把 Agent 的形态交给模型默认值

镜 1 是最好的反面教材：开发者以为"我定义了四个工具，它就是个天气助手"。 实际没有 system 的 Agent 没有身份，模型按通用助手的默认来：你的工具给了它联网能力，它就把整个产品变成"能查一切的搜索引擎"。 工具清单决定 Agent 能做什么；system 决定 Agent 该做什么——两者缺一不可。

挑战 A（必做，约 15 分钟）· 给你自己的天气循环装一份"顶层章程"

回你的 code/0001-minimal-agent.py（含 get_weather / get_current_time / report_weather，现在没有 system）。给它加一份顶层 system：

  1. 定位 + 边界：你是「天气与时间」专用助手，只处理查天气（仅支持：北京、上海、巴黎、纽约）与查当前时间；与天气、时间无关的请求（写作、闲聊、知识问答等）不要调用任何工具，直接告诉用户你只负责天气和时间。
  2. 流程纪律：查天气：先 get_weather 取回真实数据，最后调用一次 report_weather 结构化收尾；查时间：调用 get_current_time 后用自然语言答复，不要套 report_weather。
  3. 把它作为 system=SYSTEM 传给 client.messages.create，然后依次问三个问题各跑一次： "帮我查一下上海现在的天气" → "东京天气怎么样" → "帮我写一首关于海的诗"。

观察并回答我：① 上海是否先 get_weather、再 report_weather 结构化收尾（出口正确）？② 东京（白名单外）被谁挡下——是 system 的边界，还是 get_weather 的白名单闸门报错？③ 关键："写诗"这句在加 system 之前，你的循环会直接写一首诗给你（第 3 课实证，无 system 时模型按通用助手默认写诗）；加上"只做天气/时间"的 system 后，它现在还会写吗？——用你手上的运行结果回答，别猜。

小坑预告：report_weather 依旧不要加进 EXEC，也记得保持第 3 课修的"出口单独 if/continue、真工具无条件 append"结构。

挑战 B（加分，约 15 分钟）· 亲手复现"desc 层管不住零工具域外"

把挑战 A 那份 system删掉，改成把同一条边界只写进各工具的 description（get_weather 说"只支持四城、别的不查"、report_weather 说"只在拿到天气数据后收尾、无关别调"），然后只问一句："珠穆朗玛峰有多高？"

跑完回答我：模型拒了还是直接答了？再解释一遍——为什么"每个工具都写清了自己的边界"，却拦不住这一句？这跟你第 2 课学的"白名单兜得住域外、兜不住域内语义错"是不是同一类道理（都是"某层防线的覆盖范围有洞"）？

本课产出

  • ✅ 把"模型的信息源"从 TOOLS 一个抽屉升级成"system + tools(desc/schema) + tool_result"的全景
  • ✅ 拿到一条能默写的分工判据：单工具 → description/schema；整台 Agent/跨工具 → system
