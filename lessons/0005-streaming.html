第 5 课 · 模块 M2 · 工程地基

字，是一个个蹦出来的：
把 Agent 切成流式输出（streaming）

前四课你的 loop 每次都是"憋一整段、一次性给你"。真实产品里没人这么干——你对着聊天框看到的字，其实是一边生成一边蹦出来的。今天拆开 streaming：它为什么让你"更早看到字"，却不改变你的 agent 逻辑。

使命：3 个月转 AI 应用工程师 约 60–80 分钟 需要：第 4 课跑通的环境（venv + 环境变量） 花费：几毛钱 token

面试官考工程细节，有句经典开场："用户说你的 Agent 每次回答前都要转圈两三秒，你怎么破？" 新手答"换个更快的模型"；老手答两个字——streaming（流式）——然后补一句更值钱的话： 流式改的是"字什么时候送到用户眼前"，不改"模型/你的 agent 怎么想、怎么算"。 本课的实验，就是让这半句看得见。

1 · 心智模型：非流式把"生成总时长"变成你的干等时间，流式把它还给用户

两种投递方式：整段等 vs 边生成边发

你不写 stream=True 时（前四课一直如此），SDK 的默认行为是： 服务器把整段回复生成完，才把完整 JSON 一次性返回给你。 于是客户端在你发出请求后的几秒里什么也拿不到——你干等的时间，约等于"模型生成到最后一个 token"的时间。

流式打开后，同一个 HTTP 响应里开始持续推送事件：模型每吐出一个 token，就被打包成一个事件发过来。 用户体感的"快"，其实是另一个指标——首字时间 TTFT（Time To First Token）：从你按下回车，到第一个字出现在屏幕上。 

非流式：  你 ——等——— 2.5s 全静默—→ 整首诗"啪"一次性出现
流式：    你 ——0.6s—→ 第一个字 → 后面的字一个个蹦 → 1.99s 蹦完整首诗
（实测：同一句"写一首十二行、每行有"浪"的小诗"，deepseek-v4-flash，数字来自本课镜 1 的一次真实运行）
一句话记忆

流式把"我等整段"变成"我先看到字"。 用户体感 ≈ TTFT（首字时间），不是生成总时长。流式并不会把总时长变短（实测两遍总耗时几乎一样）， 它变的是空窗期——那一两秒的"沉默转圈"被逐字蹦出的字填上了。

打开引擎盖：一次"生成"，其实是一串"分块增量"事件

无论流式与否，模型产出的内容都是按内容块（content block）组织的： 一段思考、一段给用户的话、一次工具调用……各有各的块。流式只是把这些块边生成边拆成碎片发出来。 事件只有六种，能默画（Anthropic 官方事件，OpenAI 大同小异）： 

message_start                        ← 一条消息开始
  content_block_start   index=0      ← 一块内容开始（thinking / text / tool_use）
  content_block_delta   index=0 ×N   ← 这一块的 N 个小增量
  content_block_stop    index=0      ← 这块内容收齐了
message_delta                        ← stop_reason（end_turn / tool_use / max_tokens）藏在这
message_stop                         ← 一条消息结束

增量（delta）本身也分三类，关键看它属于哪一块、给谁看：

  1. text_delta —— 给用户看的字，一到就能显示。镜 2 实测一条"收到收到"被拆成两个 text_delta 碎片：'收到'、'收到'。
  2. thinking_delta —— 模型的思考碎片，通常不展示给用户。flash 在正片前常先吐一整段 thinking（本课镜 3a 实测前导 19+ 段增量）。
  3. input_json_delta —— tool_use 块参数的半截 JSON，收到一半不能解析、更不能执行（见下）。

工具参数也是"半个半个"来的——流式省不掉工具那一拍

模型决定调 get_weather 时，参数的 JSON 在流里被拆成一片片到达。镜 3a 实测碎片： 

input_json_delta 碎片：'{'   '"'   'city'   '"'   ': '   '"'   '北京'   '"'   '}'
                                 ↓ 全部拼起来
                          '{"city": "北京"}'      ← 收齐才能 json.loads / 执行！

这带出一个对 Agent 至关重要的事实：文字可以"边蹦边看"，工具调用不行。 就算参数是流式到的，你也必须等 content_block_stop 把它拼成完整 JSON，才能 EXEC[name](**block.input)。 也就是说：对"要调工具的那一拍"，流式帮不上忙——那一拍的耗时由"模型把参数想完 + 工具执行 + 结果喂回"决定，跟字传得快不快无关。 （能流式的，是工具调用前那几句给用户的圆场话。）

收尾彩蛋：get_final_message() 让流式变成"改一行就切回来"

手写循环很啰嗦？Anthropic SDK 给了你一个高级助手 client.messages.stream(...)：调用字段和 client.messages.create 一字不差，只是外面套了个 with，里面多了两个好用的东西： 

with client.messages.stream(model=MODEL, max_tokens=4096, tools=TOOLS,
                            messages=messages, system=SYSTEM) as s:
    for chunk in s.text_stream:      # ① 只吐"给用户看的字"（thinking 已自动剥掉）
        print(chunk, end="", flush=True)
    response = s.get_final_message()  # ② 把流拼回一个"和非流式 response 形状一模一样"的对象

get_final_message() 返回的对象带 .content（含 ToolUseBlock.input 已是 dict）、 .stop_reason、.usage——跟你前四课用的非流式 response 是同一种对象。 这意味着你 0001 那套 agentic loop 的 if stop_reason == "tool_use" 等逻辑一行都不用改， 只换"这一轮怎么收 response"。这就是本课核心的工程含义：

本课一句话核心（请记到能默写）

流式是 I/O / 体验层的开关，不是新的 agent 机制。 模型照常"点单 + 说话"；流式只改"字什么时候到你屏幕"。给用户看的文字可以逐字蹦；但 tool_use 参数必须攒齐整段 JSON 才能执行—— 所以工具那一拍省不掉。切流式 = 换一种收 response 的姿势 + 顺带把字实时打出来，agent 逻辑原封不动。

诚实提醒（教师实测，必读）：别把"两个副作用"赖到流式头上

① 两次跑内容不同，是抽样噪声，不是流式改的。镜 1 里非流式写出一首 168 字的诗、流式写出另一首 178 字的—— 模型每次抽样本来就不同；流式只改投递，不改生成。比时间、比事件，别比文本。② 首字延迟会波动。 flash 默认常先吐一段 thinking，首段可见文字要等它想完才来（本课多次实测首字 0.6s–1.3s 之间波动）。 想演示"字立刻蹦"，可显式 thinking={"type":"disabled"}；真实产品是否关掉 thinking 是产品决策，不是流式的锅。

# 镜 1 · 同一句"写十二行诗"，非流式 vs 流式各写一次 —— 感受"干等"vs"蹦字"
非流式 → 你干等 2.x 秒，整首"啪"地出现        （你等的其实是最后一 token 的时间）
流式   → 首字 ~0.6s 就到，后面一个字一个字蹦     （总耗时 ~2s，和不流式差不多）
        盯：首字时间 vs 总耗时；两首诗内容不同是抽样噪声，别比内容。

# 镜 2 · 打开引擎盖：裸 create(stream=True) 逐事件打印（已关 thinking 让序列干净）
你只会看到六种事件：message_start → content_block_start(index, text)
  → content_block_delta(text_delta) ×N → content_block_stop
  → message_delta(stop_reason=end_turn) → message_stop
        盯：一段 text 是由很多个 text_delta 碎片拼成的；stop_reason 在 message_delta。

# 镜 3 · 带工具：tool_use 参数是"半个半个"到的
3a 裸流 + get_weather：前导一段 thinking_delta（已折叠提示），然后
   input_json_delta 碎片 '{' '"' 'city' '"' ': ' '"' '北京' '"' '}'  → 拼成完整 JSON
3b 高级助手 messages.stream()：text_stream 只吐给用户看的字（thinking 已剥），
   get_final_message() 返回 stop_reason=tool_use，里面 ToolUseBlock.input 已是 dict
        盯：3a 里"半个 JSON"绝不能执行；3b 里你一行没手工拼，dict 直接到手。

# 镜 4 · 决定性：同一份 agentic loop，一个 streaming 开关，跑两遍同一句"上海天气"
两遍的工具调用序列、结构化出口必须逐字一致：
   get_weather({'city': '上海'}) → report_weather({...}) → ✅ 结构化出口 {...}
        盯：日志是否完全一致？一致 = 流式只改了投递，没改 agent 逻辑。
陷阱①：以为"streaming 了，工具也快了"

镜 3 的碎片就是证据：文字能边蹦边看，工具不行——参数收不齐就不能解析、不能执行。 所以一个要查天气的回合，圆场话（若有）会先逐字蹦给你看，但真正的答案永远要等 get_weather 执行完、 下一轮模型把 report_weather 交回来。流式能优化的，是"模型纯输出文字的回合"（比如长答案、逐字稿、拒绝话术）。

陷阱②：把 text_stream 当成能直接拼出工具参数的通道

text_stream 只吐给用户看的 text 块，thinking 和工具参数都被过滤掉了。 想要工具参数，别去流里捡碎片——在 with 里收完直接 get_final_message()， 从返回对象的 ToolUseBlock.input 拿现成的 dict 即可（镜 3b / 镜 4 就是这么干的）。

挑战 A（必做，约 15 分钟）· 手术刀式地把 0001 切成流式

打开 code/0001-minimal-agent.py（第 4 课成品态：有 SYSTEM_SCOPED、出口结构完好）。你要改的只有一处 API 调用点，其余一行不碰：

  1. 找到唯一那行 response = client.messages.create(model=..., max_tokens=4096, tools=TOOLS, messages=messages, system=SYSTEM_SCOPED)。
  2. 把它换成流式收 response（字段一字不差，只套 with）：
with client.messages.stream(model=MODEL, max_tokens=4096, tools=TOOLS,
                            messages=messages, system=SYSTEM_SCOPED) as s:
    for chunk in s.text_stream:            # 给用户看的字逐字打出来（thinking/参数不会混进来）
        print(chunk, end="", flush=True)
    response = s.get_final_message()       # 与非流式 response 同形状，下面代码全不用改
  1. 唯一要收拾的尾巴：end_turn 分支里原来最后那句 print("最终答案:", final) 会把已经逐字蹦过的文本再打一遍。既然字已经实时给用户看过了，这句要么删掉、要么只在没蹦过字时兜底打印。
  2. 依次问三句各跑一次（沿用第 4 课成品态的三句）："帮我查一下上海现在的天气" → "东京天气怎么样" → "帮我写一首关于海的诗"。

挑战 B（加分，约 10 分钟）· 让它"蹦到一半就断"

流式把第 3 课埋的 max_tokens 截断问题，从"静默"变成"看得见"。另存一个小文件 code/_truncate.py 跑：

import anthropic, sys
sys.stdout.reconfigure(encoding="utf-8", errors="replace")
c = anthropic.Anthropic()
with c.messages.stream(model="deepseek-v4-flash", max_tokens=16,
                       thinking={"type": "disabled"},
                       messages=[{"role": "user", "content": "请写一篇 300 字散文《窗外》"}]) as s:
    for ch in s.text_stream:
        print(ch, end="", flush=True)
    fin = s.get_final_message()
print(f"\nstop_reason={fin.stop_reason}")

跑完回答我：① 文字是不是蹦到半句就戛然而止？stop_reason 是什么？（实测停在"午后的…"，stop_reason=max_tokens。）② 为什么这段"断了"在你眼里比非流式更扎眼——非流式下截断会是什么样？（整段憋完才给你，少了尾巴你常常察觉不到。）③ 生产代码为什么无论流式与否，都必须在收尾查 stop_reason != "end_turn" 来发现截断 / 拒答？（提示：想想第 3 课"thinking 也吃这同一个预算"。）
