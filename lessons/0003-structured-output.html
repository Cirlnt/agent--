第 3 课 · 模块 M2 · 工程地基

让模型交出结构化数据：
三种拿 JSON 的姿势

前两课管住了"输入"：工具该不该调、参数传得对不对。这一课接管"输出"——当程序需要的不是一句人话，而是一份能直接拿去用的结构时，你会看到：最稳的那份 JSON，不是模型"说"出来的，是它"交"出来的。

使命：3 个月转 AI 应用工程师 约 60–80 分钟 需要：第 2 课跑通的环境（venv + 环境变量） 花费：几毛钱 token

面试官考 tool calling 时，有两个姊妹题："怎么让模型稳定调对工具、传对参数？"（第 2 课） 和 "怎么让模型稳定吐出一份可直接解析的 JSON？"（本课）。 新手对付第二题是写 prompt："请只输出 JSON，不要别的文字"； 老手的答案你没猜错——还是把 schema 当合同，靠契约不靠祈祷。今天把这句话从"输入侧"原样搬到"输出侧"。

1 · 心智模型：程序要的是"数据"，模型给的是"文本"

先分清：你要的是人话，还是能直接用的结构？

一个 LLM 应用，大多数时候不是为了让你"读一段话"。你把模型输出要喂给下游： 存进数据库、调一个函数、渲染成表格、或喂给下一个组件。下游要的不是句子，是结构。 拿一句用户话举例——"帮我查一下后天上海天气怎么样"——真正有用于下游的是抽出来的这份 dict： 

{
  "action": "查天气",
  "target": "上海",
  "when":   "后天",
}

这就是"意图路由"：很多真实 Agent 的第一站，就是把自由文本翻译成结构化指令，再拿去决定"该调哪个工具、传什么参"。 问题只剩一个：这份 dict 怎么到手？

三条路，从软到硬

  1. 姿势① 用嘴求它："只输出 JSON" → 它给你的是一段文本。 文本就得再解析（json.loads），而"模型写的 JSON 好不好解析"完全不在你控制里——它可能加围栏、加前后缀、多一个尾逗号，甚至被 max_tokens 截断成空。软，赌模型守规矩。
  2. 姿势② 工具即输出（本课主菜）：把结构定义成一个"输出工具"，让模型"要回答就必须调用它"。 于是它把答案装进工具参数，你从 block.input 拿到的天生就是 dict——因为工具调用本来就是机器通道，JSON 的编解码由端点替你完成，还受 input_schema 的 required / enum / 类型约束。硬。
  3. 姿势③ 服务端"强制"开关：Anthropic 的 tool_choice 指名、OpenAI 的 response_format + strict——在服务端就把"不走这个格式"挡掉。最硬，但每个端点实现不一样，要实测别假设（本课实验你会撞到一次 400）。
一句话记忆 / 反直觉核心

tool_use 块，本来就是免费的结构化输出。 你在第 1、2 课已经在用了——每次模型调 get_weather，它传回来的 block.input 就是一个已经解析好的 dict， 你从来没对它做过 json.loads。本课只是把这个现成通道反过来用于"输出"： 定义工具不是为了"让它做事"，而是为了"让它把答案交给你"。

同一套工具机制，输入输出两个用途

输入端（第 2 课）：模型想"用工具做事"
  你定义 get_weather 的 schema → 模型把参数 city 传回 → 你 EXEC 执行，喂回结果

输出端（本课）　：模型想"把答案交给你"
  你定义 submit_request 的 schema → 模型把答案(action/target/when)装进参数传回 → 你不"执行"，直接读 block.input

同一个机制（tool_use + input_schema），差别只在你这一侧怎么处理它。

第 1 课强调过"模型从不执行工具，只点单"——当时你把这当安全边界；本课你会发现它正好也是自由度的来源：正因为工具调用可以不触发任何副作用，它才能被当成一条纯数据通道用。

诚实提醒：工具即输出 ≠ 一定走工具（三句话记牢）

① 模型也可能直接开口说话（end_turn 给你一段文字）而不调用你的输出工具。所以镜 3 才用 tool_choice 尽量逼它；生产上你要自己检查 stop_reason，发现没走工具就重试或报错。
② "强制"开关看端点。DeepSeek 的 Anthropic 兼容端点实测：指名强制 tool_choice={type:"tool",name:...} 会 400（报错 "Thinking mode does not support this tool_choice"），而 tool_choice={type:"any"} 可用。真 Anthropic / OpenAI 又各有实现。别照搬文档假设，在你自己端点读报错。
③ schema 管"格式"，管不了"内容对不对"。拿到 dict ≠ 全对（还记得第 2 课的"域内就近偷换"吗？）——格式稳了，语义对不对要靠 eval 盯。一个连模型都推不出的"必填字段"，只会逼它编一个假的（幻觉），所以 required 要慎用。

3 · 动手：同一句"人话"，三种姿势拿 JSON（约 30 分钟）

核心思想：解析对象不是模型"说的文本"，就是从模型"交的参数"里取。同样一个问题，三种拿法，你亲手看差别。

（和镜 2 一样拿到 dict；stop_reason = tool_use）

# 小实验 · 指名强制 tool_choice={type:'tool',name}（Anthropic 写法）
端点返回：400 "Thinking mode does not support this tool_choice"

盯着 1c 多看两秒：不是你哪句 prompt 写错了——是你让模型"又说话又给 JSON"，它两样都做了，文本就不再纯净。 真实项目里开发者经常这样顺口加一句"回复礼貌一点/顺便解释一下"，于是解析就埋雷。这跟第 2 课的结论一致：模型不是坏，是它的输出天然是文本，格式由它赏。

陷阱①（教师实测，必读）：裸文本还要跟"思考"抢 token 预算

你用的是带 thinking 的模型。实测：max_tokens 给太小（如 512）时，它可能把预算全花在"思考"上，一个字正文都没吐出来，返回 stop_reason = max_tokens + 空文本——json.loads("") 直接崩。 所以课件脚本里我把裸 JSON 的预算提到了 4096。生产教训有两条：① 给足预算；② 永远先查 stop_reason（还记得第 1 课代码里那个"意外停止"分支吗？它就是干这个的）。而工具通道不受这个"与思考抢文本预算"的问题影响——工具参数是结构，跟着 tool_use 一起回来。

陷阱②：additionalProperties:false 不是物理拦截（教师实测）

第 2 课留过这个钩子。实测结论：additionalProperties:false 写在 schema 里，本端点不会替你物理拒掉多余字段——模型真想把"预算 3000、靠窗"也塞进去时，它不大会硬加一个 schema 外的键，而更可能塞进某个自由文本字段里（镜 1b 的 target 就是这么把话都吞进去的）。这又是第 2 课"最省力偷换"的一个变体。 所以它的定位是：告诉模型（和人）"合同不欢迎多余字段"的声明；要不要真拦，靠你自己代码里验一遍。第 2 课那道白名单闸门，思路一模一样，只是这回验的是输出。

挑战 A（必做，约 15 分钟）· 给天气循环装一个"结构化出口"

回你的第 1/2 课循环脚本（那个会查天气的 minimal_agent.py）。它现在查完天气是用自然语言结语收尾的。我们给它加一个"出口工具" report_weather，让模型把最终答案以结构化字段交出来，而不是说一段人话。

  1. 在 TOOLS 末尾追加一个出口工具： 
    TOOLS.append({
    "name": "report_weather",
    "description": "★最终出口★ 已经查到天气、准备答复用户时，必须调用本工具把最终结果"
                    "以结构化字段提交；提交后不要再输出任何自然语言总结。",
    "input_schema": {
        "type": "object",
        "properties": {
            "city":      {"type": "string"},
            "condition": {"type": "string",
                             "description": "从 get_weather 拿到的天气串，形如：多云，23°C"},
        },
        "required": ["city", "condition"],
    },
})
  2. 在拿到 response 之后、处理 tool_use 之前，加一段"出口检测"：一旦发现模型调了 report_weather，就把它当最终答案，打印后退出循环（不要把它当普通工具去 EXEC 执行）： 
    exit_payload = None
for block in response.content:
    if block.type == "tool_use" and block.name == "report_weather":
        exit_payload = block.input     # 出口工具：数据在参数里，不用"执行"它
if exit_payload is not None:
    print("✅ 结构化最终输出：", exit_payload)
    break
  3. 问它："帮我查一下上海现在的天气"，跑。

观察并回答我：① 模型是不是先调 get_weather、再走 report_weather 收尾？② 最终答案现在是文本还是 dict？③ 哪天它偷懒没走 report_weather、直接用自然语言结束了（stop_reason = end_turn），你的程序能发现吗？——想一想：对"必须结构化"的任务，生产里该怎么兜住第③种情况？（提示：查 stop_reason 是不是 tool_use，不是就重发一次提示或报错。）

小坑预告：report_weather 不要加进 EXEC（它不该被"当工具执行"，它是数据出口）；挑战 A 第 2 步的检测放在 EXEC[block.name](**block.input) 之前即可。

Tool use — Claude（Anthropic 官方文档）
这次精读 "Forcing tool use" 与 tool schema 段落：看官方如何用"定义一个工具 + tool_choice"来做结构化输出——你会发现你今天手写的出口工具，就是官方推荐姿势的简化版。官方那句 "the tool use API returns JSON that adheres to your schema"，正是本课"工具即输出"的依据。

厂商对照（求职加分，知道映射即可）：Anthropic 没有独立的 "JSON mode"，结构化输出=工具即输出；OpenAI 提供原生的 response_format: {"type": "json_schema"}（老版 json_object）+ strict: true 服务端强校验，可对照 OpenAI Structured Outputs 文档 看。概念一一对应，实现名不同——而你的 DeepSeek 端点两者都不完全一样，这正是要"实测别假设"的活例子。
