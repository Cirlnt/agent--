第 2 课 · 模块 M2 · 工程地基

工具的说明书：
description 与 schema 的雕琢

第 1 课的循环只保证"能调工具"。这一课解决"调得准、传得对"——而你马上会看到：答案不在模型里，在工具的那张三行字说明书里。

使命：3 个月转 AI 应用工程师 约 50–70 分钟 需要：第 1 课跑通的环境（venv + 环境变量） 花费：几毛钱 token

面试官考 tool calling 时最常追问："你怎么保证模型稳定地调对工具、传对参数？" 新手会把希望寄托在"换个更聪明的模型"上；老手会反手掏出工具的 description 和 input_schema。今天我们就看看，为什么这张"说明书"值得像雕琢玉器一样对待。

1 · 心智模型：模型看你的工具，只有一张"说明书"

它对 get_weather 的全部了解，就是你给的那三行字

第一课我们讲过：模型从不执行工具，它只"点单"。那它是根据什么决定"点哪个菜、怎么点"的？ 很多人以为是"函数写得清楚、docstring 写得详细"。错了—— 函数体、docstring、你写在注释里的提醒，模型一个都看不到。 它对一个工具的全部了解，是 TOOLS 列表里那一个字典的三个字段： 

TOOLS = [{
  "name": "get_weather",            # ① 名字：让模型认出"该调它"
  "description": "查询某城市天气…",    # ② 说明书正文：软引导
  "input_schema": {…参数怎么写…},      # ③ 参数清单：强约束
}]
一句话记忆

工具的真实行为写在你的代码里；工具在模型眼里的形象，只由这三行字决定。 说明书与实际能力对不上，模型就会"按说明书点单、点出一个你做不出的菜"。

三个字段，三种不同的"力道"

  • name（名字）——让模型在工具清单里一眼认出该调它。用"动词+名词"，如 get_weather、send_email。别起 handle_info、do_thing 这种"谁都能是它"的名字。
  • description（正文）——软引导：模型"倾向"着做对。写得好，它大多会照办；但它只是"倾向"。
  • input_schema（参数清单）——强约束：直接把"模型能传什么"框死。type、required、enum 一上，模型想传非法值都传不出来。
反直觉提醒：最值钱的是"负例"和"锁"，不是文采

新手雕 description，多半在纠结"措辞够不够像人"。其实模型乱调工具，九成不是因为没看懂你的话，而是因为你没告诉它"什么时候别用它、它做不到什么"。 这一课核心就两句：
① description 里最值钱的是负例（不支持的输入、不该调用的场景）；
② 能靠 schema 锁死的，就别靠 description 劝说——工程上这叫"靠契约，不靠祈祷"。

好 description 的四问清单（收藏它，写任何工具都用得上）

写 description 前，逐条回答下面四问，把它们落进文字里：

  1. 什么时候该用它？ 触发条件要具体："用户问某城市天气时"，而不是"用户需要信息时"。
  2. 它返回什么？ 让模型知道"这东西够不够回答用户"。返回格式给个样例："形如：晴，18°C"。
  3. 它的边界是什么？ 支持哪些、不支持哪些（负例！）。"仅支持：北京、上海、巴黎、纽约"。
  4. 什么时候不该用它？ "用户问其它城市，直接告诉暂不支持，不要调用本工具。"——这一句能救你一整晚。

schema 是"合同"：它必须和你的函数签名对齐

别忘了第一课的安全边界：模型点单，你做菜。模型按 schema 猜参数，你的 EXEC[name](**block.input) 按函数签名接单。 这两套"词"是同一份合同的两面——input_schema 说 city 是必填 string，你的 def get_weather(city: str) 就真的得能接一个 string 且不许是 None。 合同对不上时，错得最隐蔽：请求不报 400，而是等你执行到那行才 TypeError 崩给你看。

3 · 动手：让同一只"锅"换三张"说明书"（约 25 分钟）

核心思想：函数一个字不改，只改 TOOLS 里的字，模型行为就会变。你亲手看一次，比我说一百句都管用。

第 1 步 · 运行三镜头实验

文件已写好：D:\agent学习\code\0002-tool-spec-lab.py。在激活 venv 的终端里跑：

python code/0002-tool-spec-lab.py

它问了同一个问题三遍——"帮我查一下东京现在的天气。"——但每遍给模型看的 get_weather 说明书不同：

# 镜头 1 · 裸奔：description 没写支持范围，schema 也没约束
{"description": "查询天气。用户问天气时使用。",
 "input_schema": {"properties": {"city": {"type": "string"}}}}

# 镜头 2 · 好 description：写明"仅支持哪几个 + 不支持时别调用"（负例）
{"description": "查询某城市的当前天气。仅支持：北京、上海、巴黎、纽约。
若用户问其它城市，本工具没有数据，不要调用，直接告诉用户暂不支持。返回形如：晴，18°C。"}

# 镜头 3 · schema 上锁：给 city 加 enum 取值集合
{"input_schema": {"properties": {"city": {"enum": ["北京", "上海", "巴黎", "纽约"]}}}}

你应该会看到类似结果（模型措辞会有出入，关键是行不行的区别）：

镜 1 · 裸奔
  ✳ 模型想调用：get_weather({'city': '东京'})     # ← 它自信点了一个你做不出的菜

镜 2 · 好 description
  ✍ 直接回答：抱歉，只支持北京/上海/巴黎/纽约，暂不支持东京。

镜 3 · schema 上锁
  ✍ 直接回答：（同样礼貌地拒绝，因为它"没法"把东京传出去）

盯着镜 1 多看两秒——这就是本课最重要的一幕：模型根本不知道"东京"不在你的表里。 说明书没写范围，它就默认什么都能查。它甚至不会因此报错，它只会自信地点单，然后把"暂无数据"当成正常结果转述给你。

诚实提醒：镜 2 和镜 3 这次可能长得一样——这不是 enum 没用

你用的 deepseek-v4-flash 相当守规矩：description 写到"仅支持这四个城市"，它镜 2 就学会了拒绝， 所以镜 2 和镜 3 的输出常常分不出高下。那 enum 是不是多余的？不是。区别在于两层：
① description 是"说服"模型——它守规矩时听话，可它是概率系统：今天守，明天换模型、换提示词、情绪化问题下可能就不守了。
② enum 是让模型在"传参通道"里根本发不出非法值——这是机械约束，不依赖它当天心情好不好。 对越界的想象，一半靠 description 的负例劝退，一半靠 schema 的锁拦死，双保险。
还想要"绝对保证"？生产环境再加一道你自己的闸（见挑战 B），以及 Anthropic 上的 strict: true（让你的 DeepSeek 端点未必支持，此处不依赖它，知道有这么个开关即可）。

挑战 A（必做，约 10 分钟）· 把第 1 课的循环文件升级成"合格的工具"

回到你的 code/0001-minimal-agent.py（那个带 get_weather + get_current_time 的真循环）。给它做三处小手术，然后跑：

  1. 给 get_weather 的 description 加"仅支持：北京、上海、巴黎、纽约"和一句负例"问其它城市时直接告知暂不支持，不要调用本工具"；
  2. 给它的 input_schema.city 加上 "enum": ["北京", "上海", "巴黎", "纽约"]；
  3. 问它："帮我查一下深圳现在天气怎么样？"

观察并回答：加了边界之后，模型还会不会傻乎乎地调 get_weather？如果不调了，最终答案是谁"说"出来的？ 这跟你第 1 课刚写完时（裸奔）问"巴黎"是同一个循环——变化只来自那几行说明书。

小坑预告：如果一次要问两个工具相关的事（如"现在几点？深圳天气呢？"），用一句话带上两个信息，而不要发两条连续的 user 消息。 你的 DeepSeek 端点宽容、能收两条连续 user；但真 Anthropic 强制 user/assistant 严格交替，两条连续 user 会报 400。写对厂商无关的代码，就从这里开始。

挑战 B（加分，约 15 分钟）· 最后一层硬约束：执行前先"验单"

模型是概率系统，终极防线不该押在它身上，而该押在你的执行代码上。给循环加一道闸：在执行工具前先校验参数，不合规就把它当成一次"工具报错"喂回去，而不是把垃圾当正常结果。把循环里执行工具那句（第 1 课代码的 output = EXEC[block.name](**block.input)）改成类似：

if block.name == "get_weather" and block.input.get("city") not in SUPPORTED:
    output = f"错误：暂不支持城市 {block.input.get('city')}。支持：{SUPPORTED}"
else:
    output = EXEC[block.name](**block.input)

然后删掉 description 里的负例、把 enum 也去掉（退回"裸奔"），再问一次"查一下东京天气"。 观察：这次即便模型又乱点东京，你的闸也会拦下它，让模型自己读出"错误：暂不支持东京"，最终老老实实告诉你支持哪几个城市。

想一想再答我：同样是为了拦"东京"，把判断放在你这边，比起祈祷模型守规矩，强在哪？如果换一个更笨的模型来点单，哪一层还会兜底？（提示：把 description 的负例、schema 的 enum、你代码里的白名单，看成三道递减的防线。）

4 · 收束：确认你"真的会了"

自我解释练习（最重要的 3 分钟）

合上代码，用你自己的话讲给空气（或发给老师我）：
"模型对一个工具的全部了解，只有 TOOLS 里的 ____ 三样。它看不到 ____。
description 是____（软/硬）引导，写它时最容易被漏、却最值钱的是____；
input_schema 是____（软/硬）约束，用 ____ 字段可以把取值框死；
它必须和我的 ____ 对齐，否则对不齐时最要命的是它____报错，而是____才崩。"
填不出来就翻回第 1 节再讲一遍——这正是把短期记忆变成长期记忆的机制。

本课产出

  • ✅ 亲手看到：函数一字不改、只改说明书，模型行为就变（镜 1 乱点东京）
  • ✅ 拿到"好说明书"配方：name + description 四问（含负例）+ schema 锁
  • ✅ 建立三道防线心智：description 劝退 → schema 锁死 → 执行前校验兜底
